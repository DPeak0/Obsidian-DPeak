## 考核背景

“星创科技”随着业务量激增，原有的单节点 MySQL 数据库已无法满足高并发读写及容灾需求。公司决定对数据库架构进行全面升级。 作为公司的核心数据库工程师，你需要主导本次架构演进，从基础的主从备份，逐步升级到最终的 MGR 高可用+读写分离架构，并具备处理突发故障的能力。
## 实验环境要求

- **服务器节点**：node1 (192.168.0.10)、node2 (192.168.0.20)、node3 (192.168.0.30)
- **操作系统**：Rocky Linux 8.4
- **数据库版本**：MySQL 8.0.21 (系统自带源)
- **网络条件**：内网互通，关闭防火墙及 SELinux

## 考核任务清单

### 任务一：基础容灾建设 —— 搭建主从复制架构

**企业需求**：为了防止单机数据丢失，公司要求在 node1（主）和 node2（从）之间建立实时数据同步。 **操作要求**：

1. 在 node1 和 node2 安装并配置 MySQL 8.0。
- node1
```bash
[root@node1 ~]# yum install -y mysql-server.x86_64
[root@node1 ~]# systemctl enable mysqld --now
Created symlink /etc/systemd/system/multi-user.target.wants/mysqld.service → /usr/lib/systemd/system/mysqld.service.
```
- node2
```bash
[root@node2 ~]# yum install -y mysql-server.x86_64
[root@node2 ~]# systemctl enable mysqld --now
Created symlink /etc/systemd/system/multi-user.target.wants/mysqld.service → /usr/lib/systemd/system/mysqld.service.
```

2. 配置 node1 为 Master（开启 Binlog，格式为 ROW），配置 node2 为 Slave（开启 relay-log，并设置为只读 `read_only = 1`）。

- node1
```bash
[root@node1 ~]# cat > /etc/my.cnf.d/replication.cnf <<EOF
[mysqld]
bind-address = 0.0.0.0
server-id = 1
log-bin = mysql-bin
binlig_format = row
EOF
[root@node1 ~]# systemctl restart mysqld.service
```
- node2
```bash
[root@node2 ~]# cat > /etc/my.cnf.d/replcation.cnf <<EOF
[mysqld]
bind-address = 0.0.0.0
server-id =2
relay-log = mysql-relay-bin
read_only = 1
EOF
[root@node2 ~]# systemctl restart mysqld.service
```


3. 创建专用的内网同步账号 `repl`。
- node1
```bash
[root@node1 ~]# mysql -uroot
mysql> create user 'repl'@'192.168.0.%' identified by '123456';
Query OK, 0 rows affected (0.00 sec)

mysql> grant replication slave on *.* to 'repl'@'192.168.0.%';
Query OK, 0 rows affected (0.00 sec)

mysql> flush privileges;
Query OK, 0 rows affected (0.00 sec)

```

4. 建立主从同步链路，并启动 Slave。 **交付标准**：在 node2 上查询 `SHOW SLAVE STATUS\G`，需截图证明 `Slave_IO_Running` 和 `Slave_SQL_Running` 均为 `Yes`。
   
- 记录主库node1的binlog坐标
```bash
mysql> show master status\G
*************************** 1. row ***************************
             File: mysql-bin.000003
         Position: 846
     Binlog_Do_DB:
 Binlog_Ignore_DB:
Executed_Gtid_Set:
1 row in set (0.00 sec)

```
- 在node2配置主库信息，建立同步链路
```bash
mysql> change master to
    -> master_host = '192.168.0.10',
    -> master_user = 'repl',
    -> master_password = '123456',
    -> master_log_file = 'mysql-bin.000003',
    -> master_log_pos = 846;
Query OK, 0 rows affected, 2 warnings (0.01 sec)

```
### 任务二：终极高可用 —— 组建 MGR 单主集群

**企业需求**：传统的双主依然面临脑裂风险，公司决定引入 node3，采用基于分布式共识算法的 MGR 集群彻底解决高可用问题。 **操作要求**：

1. 清理前两节的主从复制旧状态。
    
2. 在三台节点上配置 MGR 核心参数（开启 GTID，配置通信种子等）。
    
3. 创建 MGR 专属同步恢复账号 `mgr_repl`。
    
4. 由 node1 引导启动集群，随后将 node2 和 node3 加入集群。 **交付标准**：执行查询集群状态的 SQL 语句，截图证明三台节点的 `MEMBER_STATE` 均为 `ONLINE`，且只有一台角色的 `MEMBER_ROLE` 为 `PRIMARY`。
    

### 任务三：流量智能分发 —— 配置 ProxySQL 读写分离

**企业需求**：集群搭建完毕后，业务代码不希望分别配置主库和从库的地址。需要部署中间件自动实现写请求打到主库，读请求分发到从库。 **操作要求**：

1. 在 node1 部署 ProxySQL。
    
2. 在集群主库创建监控账号 `monitor` 和业务账号 `app_user`。
    
3. 在 ProxySQL 中配置 MGR 节点组（写组 10，读组 20）。
    
4. 编写查询路由规则：普通 `SELECT` 路由到读库组，包含 `FOR UPDATE` 的语句路由到写库组。 **交付标准**：通过 ProxySQL 业务端口 (6033) 分别执行普通查询 `SELECT @@server_id;` 和排他锁查询 `SELECT @@server_id FOR UPDATE;`，截图展示两次查询打向了不同的服务器节点 (server_id 不同)。
    

### 任务四：故障演练与修复 —— MGR 备库遗留表冲突处理

**企业需求**：由于历史遗留问题，node2 上意外存在一张 `t1(id, name)` 表。当主库发起创建 `t1` 表的操作时，导致 node2 节点同步崩溃并掉线。你需要紧急修复此问题。 **操作要求**：

1. 模拟上述冲突环境（在 node2 关闭 Binlog 临时创建 t1 表，然后在主库执行建表 t1）。
    
2. 当发现 node2 状态变为 `ERROR` 或下线时，进行紧急排雷修复。
    
3. 清理冲突表，并让 node2 重新以健康状态加入集群。 **交付标准**：简述修复该问题的核心操作步骤（需体现如何绕过 Binlog 记录删除错误表），并截图展示修复后三台节点再次全部恢复 `ONLINE`。
